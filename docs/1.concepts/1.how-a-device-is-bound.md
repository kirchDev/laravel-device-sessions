---
title: 'How a device is bound'
description: 'How a request finds its device row, why remember-me tokens live on that row, and what revoking a device does and does not end.'
---

Stock Laravel keeps one `remember_token` per user. Every browser that ticked "remember me" holds the same value, so the token cannot say which browser presented it, and nothing can withdraw it from one browser without withdrawing it from all. This package moves the token off the user and onto a **device row**, one per browser, identified by a long-lived device cookie.

## How it works

```
request
   │
   ▼
DeviceResolver::resolveOrCreate($user, $request)
   │
   ├─ 1. device cookie  ──► an active row of this user with that id?
   ├─ 2. bootstrap cache ─► the id cached for (user, session id)?
   └─ 3. neither        ──► a new row
   │
   └─► user agent, OS family and masked IP refreshed on the row
```

Three callers run that resolution, and each one covers a moment the others cannot reach:

- **The auth provider** (`device-aware-eloquent`) resolves the device when Laravel issues a remember token, queues the device cookie if the browser does not carry the right one yet, revokes the device's previous token and stores the new one hashed. On the way back in, a remember cookie is only accepted together with the device cookie of the row it belongs to.
- **The middleware** (`TrackAuthenticatedUserDevice`) resolves the device on every authenticated request, re-queues a missing or stale cookie, and touches the row's timestamps — throttled, see [What a device row records](/concepts/what-a-device-row-records).
- **The Fortify bridge** resolves the device at the two-factor challenge, because Fortify stops the login before the `Login` event fires and the cookie would otherwise not exist when the remember token is bound afterwards. Another two-factor flow needs its own bridge: [Bridge another two-factor flow](/guides/bridge-another-two-factor-flow).

## Why it's built this way

**The bootstrap cache exists for the gap before the cookie arrives.** A queued cookie reaches the browser with the response, so a second resolution in the same session — the login request and the two-factor request, typically — would find no cookie yet and mint a second row for the same browser. Caching the resolved id per user and session id for `cache.bootstrap_ttl` seconds lands both on one row. Keep this step in any custom `DeviceResolver`.

**One active token per device.** Issuing a token revokes every other active token of that device first, so a token is never shared between browsers, and revoking one device leaves the user's other remembered browsers signed in — which the single column could not offer. The device rows are the only place a token lives. The user's own `remember_token` column is cleared when the provider loads a user who still carries a value from before the switch — Laravel would otherwise see a token already set and never issue one — and the token the guard sets on the model is kept out of any later `save()`.

**Revoking a device ends remember-me, not a live session.** `RevokeUserDevice` marks the row and its tokens revoked, so that browser can no longer come back through a remember cookie. A session that is still open is untouched: on its next request the middleware skips the revoked row and creates a fresh one. To sign a browser out now, pair the revoke with Laravel's own session invalidation — `Auth::logoutOtherDevices()`, which needs the `auth.session` middleware on the routes it should protect, and whose `OtherDeviceLogout` event this package answers by revoking every other device (on by default, `device-sessions.events.*`).

**Revoked rows are kept, then pruned.** They stay readable as an audit trail until `device-sessions:prune` removes them after `prune.retention_days`; the command ships unscheduled.

To put a device list in front of a user, see [Build a device list page](/guides/build-a-device-list-page).
