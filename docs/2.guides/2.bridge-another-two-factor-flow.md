---
title: 'Bridge another two-factor flow'
description: 'Bind the device before the login completes when two-factor authentication does not come from Fortify.'
---

A two-factor step interrupts the login after the password check and before Laravel's `Login` event — and before the device cookie would otherwise exist. Fortify gets a bridge automatically; any other flow needs the same three lines at its own challenge point ([why the gap matters](/concepts/how-a-device-is-bound)).

## Steps

1. **Find the moment the challenge is issued.** That is the request that has identified the user but not logged them in: an event your two-factor package fires, or the controller action that renders the code form.

2. **Resolve the device and queue its cookie there.** Resolve both collaborators from the container, so a rebound resolver or cookie policy applies:

   ```php
   use Illuminate\Support\Facades\Cookie;
   use KirchDev\DeviceSessions\Contracts\DeviceCookieFactory;
   use KirchDev\DeviceSessions\Contracts\DeviceResolver;

   $device = app(DeviceResolver::class)->resolveOrCreate($user, $request);

   Cookie::queue(app(DeviceCookieFactory::class)->make($request, (string) $device->getKey()));
   ```

3. **Let the login complete as usual.** When the code is accepted and the login runs with "remember me", the provider resolves the device again — through the cookie if the browser already returned it, otherwise through the bootstrap cache — and binds the token to the same row.

4. **Keep the session id stable across the two requests**, or keep the gap shorter than `cache.bootstrap_ttl`. The bootstrap cache is keyed on the user and the session id; a flow that regenerates the session between challenge and completion, before the cookie has come back, loses that fallback.

## Checklist

- [ ] The bridge runs where the user is known but not yet logged in.
- [ ] `DeviceResolver` and `DeviceCookieFactory` come from the container, not their default classes.
- [ ] After a remembered two-factor login, the user has one device row, not two.
- [ ] The session id survives until the device cookie is back, or the gap fits `cache.bootstrap_ttl`.
